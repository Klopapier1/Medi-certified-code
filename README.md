# Medi-certified-code

AI orchestration framework that produces medical device software alongside the traceable evidence package (requirements, design, tests, risk analysis, traceability) needed to pursue certification under IEC 62304.

> **Not a certification authority.** No AI pipeline can grant medical device certification — that's a regulatory act performed by a notified body / competent authority against a real Quality Management System. This framework produces the software engineering evidence a human Regulatory Affairs / QA reviewer needs to pursue that certification, and nothing here is final until a human signs off. See [`docs/mvp-scope.md`](docs/mvp-scope.md) for the full rationale.

## Overview

Given a plain-language description of one software item, the pipeline runs eight sequential stages — five driven by Claude, three by real tooling — and writes a complete, cross-referenced evidence package:

1. **Requirements** (LLM) — plain language → a Software Requirements Specification with stable `REQ-*` IDs
2. **Design** (LLM) — SRS → a Software Design Description traced to those IDs
3. **Code generation** (LLM) — SDD → implementation, each unit citing the requirement/design ID it implements
4. **Static analysis** (real tooling — `ruff`, `mypy --strict`) — actually run against the generated code, not self-reported
5. **Testing** (LLM writes tests, real `pytest` executes them) — actual pass/fail and coverage, not claimed by the model
6. **Risk analysis** (LLM) — an ISO 14971–informed hazard table for the item
7. **Evidence compilation** (mechanical, regex-based) — a traceability matrix built by scanning `REQ-*`/`D-*` IDs across every artifact, not asserted by an LLM
8. **Human gate** — a blank sign-off template; the package stays "draft" until a person fills it in

## Features

- **Product-agnostic engine.** The `orchestrator/` package contains no domain-specific content — it only knows the 8-stage process and a fixed artifact layout. Every generated item lives under `products/<name>/`, fully separate from the framework code.
- **Verification you can trust.** Test execution and static analysis are real subprocess runs, not an LLM's claim about its own output. The traceability matrix is compiled by scanning files for ID strings, not generated by a model.
- **Fails fast, writes nothing on error.** Missing `ANTHROPIC_API_KEY` raises before any file is touched.
- **Mandatory human gate.** Every run ends with a blank `evidence/review-signoff.md` — the pipeline never marks its own output as approved.
- **Scoped to IEC 62304 Class A** for the MVP (software whose failure cannot cause injury). Class B/C support needs risk-based branching this pipeline doesn't implement yet.

## Architecture

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│         orchestrator/        │ writes │        products/<name>/        │
│  (framework, product-agnostic)│ ─────► │  (one pipeline run's output)   │
│                               │        │                                │
│  config.py   — ProductSpec    │        │  requirements/SRS.md           │
│  client.py   — Claude API      │        │  design/SDD.md                  │
│  roles.py    — prompt templates│        │  src/<name>.py                  │
│  tools.py    — pytest/ruff/mypy│        │  tests/test_<name>.py           │
│  evidence.py — traceability   │        │  evidence/*.md, *.json          │
│  pipeline.py — the 8 stages   │        │                                │
│  cli.py      — entrypoint     │        │                                │
└─────────────────────────────┘        └──────────────────────────────┘
```

The framework never imports from or references `products/`; a product directory never contains framework code. Deleting any one product doesn't affect the framework or any other product.

## Installation

```bash
git clone <this-repo>
cd Medi-certified-code
pip install -r orchestrator/requirements.txt   # anthropic, python-dotenv
pip install -r requirements-dev.txt            # pytest, ruff, mypy — for verifying generated products
```

## Configuration

The pipeline reads its configuration from environment variables. A `.env` file in the repo root is loaded automatically if present (via `python-dotenv`) — copy `.env.example` to `.env` and fill it in, or export the variables directly.

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | Yes, for any run | — | Claude API key for the five LLM-driven stages. Missing key raises `MissingAPIKeyError` before anything is written. |
| `ORCHESTRATOR_MODEL` | No | `claude-sonnet-5` | Default model id, overridable per run with `--model`. |

`.env` is gitignored — never commit real credentials.

## Usage

```bash
python3 -m orchestrator.cli \
  --name bmi \
  --requirement "Calculate BMI from height and weight." \
  --output-dir products/bmi \
  --safety-class A
```

```
Done. Evidence package written to products/bmi
Reminder: nothing here is final until a human completes products/bmi/evidence/review-signoff.md
```

A ready-to-run example of this same command, with its input already filled
in, lives in [`demo/`](demo/) — see [`demo/README.md`](demo/README.md).

## Input

The pipeline's only input is a `ProductSpec` (`orchestrator/config.py`), populated from CLI flags:

| Field | CLI flag | Type | Required | Default | Notes |
|---|---|---|---|---|---|
| `name` | `--name` | `str` | Yes | — | Must be a valid Python identifier; becomes the module name (`src/<name>.py`) and test file name |
| `plain_requirement` | `--requirement` | `str` | Yes | — | Plain-language description of what the item should do |
| `output_dir` | `--output-dir` | `Path` | Yes | — | Where the artifact tree is written, e.g. `products/bmi` |
| `safety_class` | `--safety-class` | `str` | No | `A` | IEC 62304 safety class; MVP only accepts `A` |
| `language` | — | `str` | No | `python` | Only `python` is supported currently |
| `model` | `--model` | `str` | No | `$ORCHESTRATOR_MODEL` or `claude-sonnet-5` | Claude model id for the generative stages |

Invalid combinations (unsupported safety class, unsupported language, non-identifier name) raise `ValueError` immediately — before the pipeline runs.

## Output

Each run writes a self-contained artifact tree to `--output-dir`:

```
products/<name>/
├── conftest.py                        # empty; makes `src.<name>` importable by pytest
├── requirements/
│   └── SRS.md                         # requirements with stable REQ-* IDs
├── design/
│   └── SDD.md                         # design, traced to REQ-*
├── src/
│   ├── __init__.py
│   └── <name>.py                      # implementation, traced to REQ-*/design IDs
├── tests/
│   └── test_<name>.py                 # tests grouped by REQ-*
└── evidence/
    ├── static-analysis-report.md      # real ruff + mypy --strict output
    ├── test-report.md                 # real pytest output (pass/fail, coverage)
    ├── risk-table.md                  # ISO 14971–informed hazard table
    ├── traceability-matrix.md         # REQ-*/D-* cross-reference, mechanically compiled
    ├── run-provenance.json            # model, timestamps, per-stage verification method
    └── review-signoff.md              # blank human sign-off template — the mandatory gate
```

| Evidence file | Produced by | Verified how |
|---|---|---|
| `static-analysis-report.md` | `ruff check`, `mypy --strict` | Real subprocess execution against the generated code |
| `test-report.md` | `pytest` + `pytest-cov` | Real subprocess execution against LLM-generated tests |
| `traceability-matrix.md` | `orchestrator/evidence.py` | Regex scan of `REQ-*`/`D-*` IDs across every artifact file |
| `run-provenance.json` | `orchestrator/evidence.py` | Records model id, date, and each stage's verification method |
| `review-signoff.md` | Pipeline (template only) | Not verifiable by the pipeline — requires an actual human |

## Project structure

```
orchestrator/            the pipeline engine (product-agnostic)
├── config.py               ProductSpec — the only place a run's parameters live
├── client.py                thin Claude API wrapper, reads ANTHROPIC_API_KEY
├── roles.py                 prompt templates for each generative stage
├── tools.py                  real pytest/ruff/mypy subprocess wrappers
├── evidence.py               traceability matrix + provenance, regex-based
├── pipeline.py                the 8-stage Pipeline class
├── cli.py                     CLI entrypoint, loads .env if present
├── requirements.txt           anthropic, python-dotenv
└── tests/                    framework's own tests (no API key needed)

products/<name>/          one software item's pipeline output (see Output above)

demo/                     ready-to-run example input (see demo/README.md)

docs/
└── mvp-scope.md            MVP scope, rationale, and open questions

requirements-dev.txt      shared dev tooling versions used to verify any product
.env.example               template for local ANTHROPIC_API_KEY / ORCHESTRATOR_MODEL
```

## Testing

Framework tests (no API key needed — cover `config.py`, `tools.py`, `evidence.py`, and `client.py`'s key-resolution logic without any network calls):

```bash
python3 -m pytest orchestrator/tests/ -v
```

A given product's own checks, e.g. the BMI pilot:

```bash
python3 -m pytest products/bmi/tests/ -v --cov=src.bmi --cov-report=term-missing
cd products/bmi && ruff check src/ && mypy --strict src/
```

## Status and limitations

- `orchestrator/` — pipeline exists end-to-end; its non-LLM stages are tested for real. The LLM-driven stages haven't been exercised against a live API in this environment (no key configured here) — they're ready to run wherever `ANTHROPIC_API_KEY` is set.
- `products/bmi/` — one Class A item taken through the full 8-stage evidence model, hand-orchestrated before `orchestrator/` existed, as proof of the artifact model. Not yet regenerated by the automated pipeline.
- No claim of regulatory submission-readiness. IEC 62304 Class B/C, non-Python targets, and integration with a real QMS are explicitly out of scope for this MVP — see [`docs/mvp-scope.md`](docs/mvp-scope.md).
